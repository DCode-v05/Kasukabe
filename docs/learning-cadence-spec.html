The 30-Minute Snapshot

A correction the user gives at 10:00 is not encoded until the batch runs — up to six hours later, or never on a session that stays busy. The snapshot idea is right and this specifies it. But the symptom you described has a second cause that no cadence change fixes, and it is one line of missing code in the read path.

DiagnosisTwo problems, not one

“The user specifies a change; the context compacts an hour later; the rule gets missed.” That sentence describes one experience and two independent defects. Only one of them is about cadence.

What is not broken: capture

The post-turn hook writes the signal synchronously at the end of the turn the correction happened in — through guard_content, into SQLite, committed. Compaction cannot lose it; the row outlives the context window by design. So the correction is safe on disk within seconds. The problem is downstream of that.

Defect one: nothing reads a signal until the batch encodes it

Coordinator.prefetch_memory fans out to → episodes · knowledge · social Search.signals() exists, FTS5 over learning_signals, never called by a turn Search.unified() calls all four — and is not the recall path
The correction is durable, searchable and invisible. Recall reads the three batch-written stores; the row sits in learning_signals being matched by nobody until the batch turns it into knowledge. That is the six-hour blind window, and it is a read-side defect — moving the batch to 30 minutes shortens it to thirty minutes but does not close it.

Defect two: the batch may not run at all

opportunity() fires on IDLE/DETACHED and is rate-limited by a 6-hour interval; final_drain() fires on QUIESCENT; loop() is a 6-hour backstop for a session that never goes idle. Ten to fifteen threads working continuously is exactly the shape that never goes idle — so the backstop is the only trigger, and it fires four times a day.

So: fix the read so a correction applies on the next turn, and fix the cadence so it becomes durable memory within thirty minutes. The first is small and immediate; the second is the snapshot design. They are complementary, and shipping only the second still leaves a turn unable to see what the user said ten minutes ago.

Fix oneThe fourth leg

prefetch_memory gains a fourth parallel call. Everything it needs already exists: the FTS5 index, the search method, a configured limit (SEARCH_UNIFIED_SIGNALS_LIMIT) and a default score for pending rows — all built for unified() and never wired to the turn.

bundle = {episodes, knowledge, social, pending, query_embedding, embedding_tokens} pending rows are LABELLED in the recall reminder: "Recent, not yet consolidated:" — so the model can weigh a raw signal against an encoded fact rather than treating them alike.

Four properties this must keep:

  • Uncached, deliberately. signals() is the one search that is not cached, because learning_signals is written on every turn and a cached pending-signal result would be stale inside the same conversation. That reasoning is already in the tree and applies doubly here.
  • Keyword-only. Signals have no embedding leg; FTS5 rank is the whole score. A small limit (start at 3) keeps a weak match from crowding out an encoded fact.
  • Correction-biased. A pending correction is worth more at recall than a pending event. Order by type before rank, or filter to the types that carry instruction.
  • Duplication is acceptable and must be visible. Once the batch encodes the signal, recall may surface both the raw row and the derived fact until the row is deleted. The label is what makes that legible rather than confusing.
Latency from “user states a rule” to “a turn can see it” goes from ≤6 hours to the next turn. No model call, no schema change, no cadence dependency.

Fix twoThe snapshot cut

Your instinct — take what exists at the tick, let in-flight writes fall into the next batch — is already how the read behaves. What is missing is that the behaviour is implicit, and three things that survive at four batches a day do not survive at forty-eight.

The snapshot you want mostly exists

run_batch() signals = pull_unprocessed() SELECT … WHERE processed = 0 ORDER BY created_at … three encoding agents run on `signals` … mark_processed(ids, batch_id) happens AFTER the agents, not before delete_processed() / unmark_processed(batch_id)

A row inserted while the agents are running has processed = 0 and is simply not in signals. It waits for the next batch. That is the “set aside whatever is currently being written” behaviour, and it needs no locking because the pull is one SELECT against a committed table. The defects are elsewhere.

RiskWhat breaks at 48× the rate

DefectWhy it is survivable todayWhy 30 minutes changes that
delete_processed() is WHERE processed = 1 — it deletes every processed row, not this batch's. Two batches almost never overlap at a 6-hour interval, so the flag effectively identifies one batch. A batch that finishes while another is mid-run deletes the other's claimed rows before they are encoded. Silent loss, no error, no log.
No overlap guard. loop(), opportunity(), trigger_now() and final_drain() all call run_batch() with nothing serialising them. Rare enough to never have been seen. A 30-minute tick plus a QUIESCENT drain plus a manual trigger is three entry points into a window that is now short. Two batches pulling the same unprocessed set means every signal is encoded twice.
The mark→delete crash window. Rows are marked processed = 1 mid-batch; if the process dies before Phase 5, no later pull_unprocessed (which reads processed = 0) ever sees them again. Four windows a day. Forty-eight. And the next successful batch's delete_processed() removes the orphans unread — the loss is completed by the recovery path.
pull_unprocessed() has no LIMIT. A 6-hour backlog is large but is pulled once. Mostly better — 30 minutes of signals is a smaller pull. But the first tick after downtime still pulls everything at once, and that is the tick that will blow the model budget.
None of these are caused by the cadence change. They are pre-existing, and the cadence change is what makes them likely. That is the honest reason this proposal is more than editing one constant.

DesignThe claim, in SQL

Move the claim from mid-batch to the cut, make it atomic, and address every later step by batch_id instead of by the flag.

1 · CLAIM one statement, at the tick UPDATE learning_signals SET processed = 1, batch_id = :batch, claimed_at = datetime('now') WHERE id IN ( SELECT id FROM learning_signals WHERE processed = 0 AND created_at <= :cutoff the snapshot line ORDER BY created_at ASC, id ASC second-resolution tiebreak LIMIT :max_per_batch ) 2 · READ SELECT … WHERE batch_id = :batch ORDER BY created_at ASC, id ASC 3 · FINISH wrote_something ? delete_batch(:batch) : release_batch(:batch) delete_batch DELETE FROM learning_signals WHERE batch_id = :batch release_batch UPDATE … SET processed = 0, batch_id = NULL, claimed_at = NULL WHERE batch_id = :batch 4 · RECLAIM on boot and in every sweep UPDATE learning_signals SET processed = 0, batch_id = NULL, claimed_at = NULL WHERE processed = 1 AND claimed_at < datetime('now', '-:stale_seconds seconds')

Why each part is there

  • created_at <= :cutoff is the snapshot line, stated rather than implied. A row written a second after the tick is outside the claim by a rule anyone can read, not by an accident of statement ordering.
  • Claiming first means an overlapping batch's claim matches zero rows — SQLite serialises the writes, so the second UPDATE simply finds nothing left. The overlap guard is the statement itself; an asyncio.Lock on top is belt-and-braces for the same-process case and costs nothing.
  • id ASC as tiebreak — created_at is second resolution and a busy engine writes many signals inside one second. Step 11 already learned this the hard way; the claim needs the same rule or the LIMIT cuts an arbitrary subset of one second.
  • delete_batch ends the cross-batch deletion. This is the one change that must land before the cadence change, not with it.
  • claimed_at + reclaim closes the crash window that currently has no recovery at all. Stale threshold well above the longest plausible batch — start at 30 minutes, i.e. one full tick.
  • LIMIT :max_per_batch makes a backlog drain over several ticks instead of one enormous call. Suggested start: 500 signals.

Schema cost is one nullable column, claimed_at, on a table that already carries processed and batch_id. One migration, no rewrite.

The scheduler change itself

lc_batch_interval_hours 6.0 → 0.5 single-source default, already read off the dataclass loop() the PRIMARY trigger now, not the backstop opportunity() kept — an idle moment inside the window is still a fine time, and it is already rate-limited by the same interval final_drain() unchanged; QUIESCENT still ignores the interval empty tick run_batch returns early when the claim is empty — free

BudgetWhat it costs

Forty-eight batches a day instead of four. The number that matters is not batches, it is model calls, and the batch's call count scales with threads — which is precisely the situation you were worried about.

calls per batch = 1 (social) + N clusters knowledge, cosine > 0.7 grouping + M threads episode, one per non-trivial thread_id with 12 active threads and 3 clusters: ~16 calls per tick ~768 calls per day vs ~64 today
That is a 12× increase in call volume, not 12× in tokens — each call carries thirty minutes of signals instead of six hours, so per-call context shrinks by roughly the same factor. Total tokens should land close to flat; total requests will not, and requests are what hits rate limits. Producing that number is the job of the companion note, Measuring What It Learns, and it has to land before the cadence flips.

Three mitigations, in the order I would apply them:

  1. Episode encoding needs a floor. One call per thread per tick is the cost driver. A thread with two new signals does not need an episode every thirty minutes — gate on a per-thread signal count or reuse the existing FLUSH_TURN_THRESHOLD watermark pattern.
  2. Batch the social call across ticks. Social extraction takes the whole signal context and runs once; at 30-minute cadence most ticks will have no new people. Skip when no signal in the claim carries a person or relationship type.
  3. Respect the quota cooldown — loop() already skips a cycle while citadel's window is exhausted. At 48 ticks a day that guard goes from theoretical to load-bearing.

HonestyWhere this could fail

Thirty minutes may be the wrong number in both directions

Too slow to feel live — a user correcting the engine expects it to stick now, and thirty minutes is not now. Too fast to be cheap — 12× the requests. The read-side fix is what makes “now” true; the cadence only has to be fast enough that memory does not drift, and 30 minutes may be over-buying. Worth testing 60 against 30 once both land.

Small batches may encode worse than large ones

Knowledge clustering groups by embedding similarity across the whole claim. Thirty minutes of signals from one thread may not cluster into anything meaningful, and consolidation explicitly looks for cross-batch patterns — a pattern spread thinner across 48 batches may be harder to see, not easier. This is measurable: run the end-to-end track with a 6-hour claim and a 30-minute claim over the same seeded corpus and compare what each produces.

The pending-signal leg could make recall noisier

Raw signals are unencoded, unranked by embedding, and sometimes wrong. Surfacing three of them every turn may crowd out better-scored encoded memory. Mitigation is the small limit and the label; the check is whether recall quality on the existing corpus moves.

What is not risky

The claim SQL, the batch-scoped delete, and the reclaim are fixes to defects that exist right now. They are worth landing whatever happens to the cadence.

  1. Batch-scoped delete and reclaim. delete_batch, release_batch, claimed_at, the reclaim sweep. Cadence untouched. Fixes real data loss today. check · two overlapping batches each keep their own rows; a batch killed after mark has its rows reclaimed and re-encoded on the next tick
  2. The fourth leg in recall. Pending signals in prefetch_memory, labelled, limit 3, correction-biased. check · a correction written this turn is present in the next turn's recall bundle, labelled unconsolidated, with no batch having run
  3. The atomic claim with a cutoff and a LIMIT. Still at 6 hours — proving the mechanism separately from the frequency. check · a signal written mid-batch lands in the following batch, never in the current one, and never twice
  4. The pipeline evaluation. Specified separately in Measuring What It Learns. It is the gate on step 5, not a report after it: a 12× rise in request volume onto an encoder whose cost and failure rate are unmeasured is a change nobody can size. check · cost per simulated tick and wall-clock per batch are known numbers before the interval moves
  5. Interval to 30 minutes, behind the setting that already exists. lc_batch_interval_hours is one value with a single source; the episode floor and the social skip land with it. check · a busy 12-thread session encodes within one tick, and the daily request count matches what step 4 predicted

Decisions I need from you

  • Should step 2 ship ahead of everything else? It is small, it is the fix for the symptom you actually described, and it is independent of the rest.
  • Is 30 the right number, or is 60? The read-side fix in step 2 is what makes a correction feel immediate. Once it lands, the batch only has to be fast enough that durable memory does not drift — and 30 minutes may be over-buying. Both are one setting.
  • Does the episode floor ship with step 5 or before it? One episode call per thread per tick is the whole cost story; a floor makes the increase far smaller than the arithmetic in §Budget suggests.
