Memory On Demand

A thread gets one shot at recall, at the top of the turn, on the user's opening words. If it misses, there is no second question — no tool, no fallback. The retrieval this needs is already written, already routed through a cache every thread shares, and called by nothing.

SummaryTwo findings first

Both halves of the request were checked against the tree. One is already done; the other is one tool away from done, because its hardest part is written and dead.

Part 1 · centralize caching done

One Search instance, constructed at boot, handed to the coordinator and to every thread. Its cache is already shared across all of them.

Part 2 · the query tool missing

No memory tool exists in the registry. A thread that misses at prefetch has no way to ask again.

The retrieval it needs dead

Search.unified() — hybrid, cross-store, cached, with entity fusion — has no callers anywhere in src/.

So this is not a build. It is a wiring job: expose retrieval that already exists, through a tool that does not, onto a cache that is already shared. The interesting decisions are about behaviour — when the model may call it, what it costs, and what it must not be allowed to do — not about plumbing.

Part oneAlready centralized

The target state described — memory operations integrated into the search.py caching layer, optimized across concurrent threads — is what the tree does today. The chain:

bootstrap.py:1800 state.search = Search(db, episodic, knowledge, social, embedder, catalog) coordinator self.search = search one object, injected every thread search=self.search the SAME object, not a copy Search.__init__ self.cache = TTLCache(default_ttl=900, max_entries=256)

Ten concurrent threads hold ten references to one Search, and therefore one TTLCache. Everything that goes through episodes(), knowledge() or social() is already shared between them, with three properties that were added deliberately and matter here:

PropertyWhat it does for concurrent threads
get_or_loadCollapses concurrent misses on one key into a single store read. Ten threads asking the same question at once produce one query, not ten.
Row-level copies (_detach)Each caller gets its own dicts, so one thread's _source tagging or social-boost rescoring cannot land in the cache and reach the next reader.
Writer-announced invalidationThe batch's on_data_changed and POST /memory/import both clear it, so the 900s TTL is a backstop rather than the whole correctness story.
LRU bound at 256Keys carry user text; recency is a read property, so the most-asked query survives eviction.
This means the cross-thread optimization in the request is not something to build — it is something the new tool inherits by calling the same accessors. The one rule to keep is that the tool must go through Search, never around it to a store, or it silently opts out of all four properties above.

The one thing that is not shared

Search.embed() keeps a separate 256-entry LRU keyed on the exact string. It is on the same object, so it is shared too — but it is keyed on exact text, so two threads asking the same question in different words share the result cache only if their phrasings match exactly. That is a cost floor on the tool: distinct phrasings pay for distinct embeddings.

DiscoveryThe retrieval that exists

Search.unified(query, limit) is the hybrid cross-memory retrieval this tool needs. It is complete, commented, configured — and nothing in the engine calls it. The only mentions of it outside its own definition are two comments in config.py describing the settings it reads.

async def unified(query, limit=20) embed once one round trip, not four gather: episodes(query, limit, emb) → cached 30% keyword / 70% semantic knowledge(query, limit, emb) → cached 30% keyword / 70% semantic social(query, limit, emb) → cached 50 / 50 signals(query, limit) → uncached FTS5 over pending signals tag each row with _source collect person names from the social leg boost episode/knowledge rows that mention those people word-boundary regex sort by score, return top-limit

Three things this gives the tool for free

  • The hybrid pipeline, unchanged. Same weights, same recency boost, same keyword fallback for rows without embeddings — the request's "re-use the existing retrieval logic" is satisfied by calling this rather than by copying anything.
  • Entity fusion. A query that surfaces a person also lifts the episodes and knowledge mentioning them. Prefetch does not do this; it fans out three ways and folds the results in flat.
  • Pending signals. unified() reads learning_signals — the rows a correction lands in before the batch encodes it. This is the exact blind spot described in The 30-Minute Snapshot: recall cannot see an unencoded correction. The dead function already reads it.
That last point makes the two specs overlap, and the overlap should be resolved deliberately rather than by both landing a fix. The cadence spec adds pending signals to the push path (prefetch); this spec exposes them on the pull path (the tool). Both are worth having — push means a correction applies without the model thinking to ask; pull means it can dig when the push missed — but they must share one labelling convention so a pending row reads the same either way.

Why it is dead, and what that implies

Nothing is wrong with it; it was written for a caller that never arrived — the same shape as four other subsystems that shipped wired to nothing and were caught in bc20dec. Two consequences worth stating before building on it: it has never run in production, and the deterministic corpus does not cover it. Treat its correctness as unverified, and give it tests as part of this work rather than assuming the code's completeness implies it works.

Part twoThe tool

name: search_memory input: query string, required what to look for, in natural language scope enum, optional all | episodes | knowledge | people | pending default: all limit integer, optional default 10, hard cap 25 behaviour: is_read_only → true is_concurrency_safe → true must not serialize a parallel batch routes to → Search.unified() (scope=all) Search.episodes/knowledge/social/signals (narrowed)

Naming

search_memory over query_memory, for consistency with the existing tool namespace: search_content, search_files, tool_search — the engine's verb for retrieval is already search. A namespace where one member says query is one people get wrong from memory. (The same argument produced read_sub_agent_output over read_subagent_output in the companion spec.)

Why scope is worth the extra parameter

unified() costs one embedding plus four store reads. A thread that knows it wants a person — "who is Priya" — should not pay for the episode and knowledge legs. Narrow scopes route straight to the single cached accessor, and the default stays all so the model never has to choose to get the good behaviour.

Output shape

Rows come back tagged with _source; the tool renders them grouped by source with the source named, and pending signals labelled as unconsolidated:

EPISODES 2026-08-14 | Debugged the payment queue race condition … KNOWLEDGE deploy cadence — the team deploys on Tuesdays (confidence 1.0) PEOPLE Priya — platform team lead RECENT, NOT YET CONSOLIDATED ← pending signals, labelled correction · "lead meeting notes with decisions, not attendees"

Confidence is shown for knowledge rows because the store distinguishes a user-stated fact (1.0) from an inference (≤0.8), and a model weighing two conflicting memories needs to know which is which. Scores are not shown — they are a ranking device, not information, and printing them invites the model to reason about numbers that mean nothing outside the sort.

MechanicsCross-thread sharing, precisely

The claim in the request — one thread's retrieval becomes instantly available to the other nine — is true, with two qualifications worth knowing before relying on it.

key mem:{kind}:{limit}:{'e'|'k'}:{query} thread 3 search_memory("payment queue race") → miss, one store read, cached thread 7 search_memory("payment queue race") → hit, no store read thread 9 search_memory("payment queue race") → hit (concurrent: get_or_load collapses to ONE read) thread 5 search_memory("payment queue bug") → miss different string, different key AND different embedding
Qualification one · the key is the exact query string

Sharing is exact-match, not semantic. Two threads investigating the same thing in different words share nothing. That is the correct conservative behaviour — a semantic cache key would need an embedding to compute, which is the expensive half of what it saves — but it means the "nine other threads benefit" case is strongest for repeated identical queries (retries, fan-out over one brief) and weakest for genuinely independent work.

Qualification two · limit and the embedding flag are in the key

A cached result for limit=10 cannot answer limit=25, and a keyword-only result is a different key from an embedded one. Both are deliberate — the stores rank differently with and without a vector. Practical effect: keep the tool's default limit fixed rather than letting the model choose freely, or every call becomes a distinct key and the sharing evaporates. Recommendation: accept limit but snap it to one of two values (10, 25) so the key space stays small.

What is genuinely free

Invalidation. When the batch writes, one on_data_changed clears the cache for every thread at once — there is no per-thread state to reconcile, and no thread can be left holding a stale view after a write it did not make.

The pending leg is uncached, on purpose

signals() is not cached because learning_signals is written on every turn, so a cached pending result would be stale inside the same conversation. With ten threads each calling search_memory, that leg is the one that scales linearly with calls. It is an FTS5 query against a table with a shadow index, so it is cheap — but it is the part of this design that does not get cheaper with sharing, and worth watching.

BehaviourWhen the model should call it

A tool the model does not know when to reach for is a tool it either ignores or overuses. The description has to name the trigger, not the capability — the same rule that makes the existing spawn_sub_agent description work.

Search durable memory — past episodes, learned facts, people, and recent corrections not yet consolidated. Recall runs automatically at the start of a turn against the user's opening words. Use this when that was not enough: the conversation has moved to a subject the opening message did not name, the user refers to something earlier you cannot see, or you need to check whether a preference or decision on this topic already exists before assuming one does not. Do not call it to confirm something already in your context.
The last line is doing real work. The failure mode of a memory tool is not underuse — it is a model that queries memory before every action, spending a store read and 300 characters of context to re-learn what it was told two messages ago. Prefetch already covers the opening; this covers the drift.

One thing it must not become

A write surface. search_memory reads. Durable memory is written by the batch, and that asymmetry is load-bearing — it is why LC-inferred knowledge is capped at 0.8 confidence while user-stated facts reach 1.0, and why nothing in a turn can promote its own guess into a permanent fact. If a "remember this" tool is ever wanted, it is a separate decision with its own confidence policy, not a parameter on this one.

HonestyWhat could go wrong

Recall noise displaces the actual task

Ten rows of loosely-related memory in the middle of a turn can pull a model off the thing it was doing. Mitigated by the low default limit, the elision, and the trigger-shaped description — but the honest position is that this is a prompt-behaviour change, and no eval here measures whether recall improves or degrades task completion. That is a gap this spec creates and does not close.

unified() has never run

Complete, configured, and unexercised. Its social-boost pass mutates score on rows it received from the cached accessors — safe today only because _detach hands out copies. That interaction has never been exercised under concurrency, and it is exactly the class of bug f91635a found by reading rather than by testing. Needs a concurrency test before it carries traffic.

Cost is per-call and unbounded across threads

One unified() call is one embedding plus four store reads. Ten threads calling it twice a turn is twenty embeddings and eighty reads per turn-round, minus whatever the cache absorbs — and the cache absorbs only exact repeats. The sharing story is real but it is not a substitute for a per-turn cap.

What is low-risk

The plumbing. One tool registration, routing to an existing method, on an existing shared cache, read-only, with no schema change and no new store.

SequencePlan

  1. Test unified() before exposing it. It has never run: cover the social-boost pass, the empty-store case, and two threads racing one key. check · concurrent identical calls produce one store read per leg; a caller's rescoring never reaches the cache
  2. Register search_memory, scope=all only. Routes to unified(), renders grouped output, labels pending rows, read-only and concurrency-safe. check · a fact written by a prior batch is retrievable mid-turn by a query that does not restate it
  3. Add the narrow scopes. episodes, knowledge, people, pending routing straight to the single cached accessor. check · scope=people performs one store read, not four
  4. Per-turn call cap and the notice. Soft, with a message naming the repetition rather than a silent refusal. check · a third near-identical query in one turn returns the cached rows plus the notice
  5. Reconcile with the push-path change. One labelling convention for pending signals across prefetch and the tool, decided once. check · a pending correction reads identically whether it arrived by push or by pull

Decisions I need from you

  • Does the tool ship before or after the prefetch pending-signal leg? They overlap on the same rows. My recommendation is push first — it is smaller and needs no model cooperation — then this as the fallback for when push misses.
  • Snap limit to two values, or let the model pass any integer? Free choice fragments the cache key space and quietly kills the cross-thread sharing this spec is partly for.
  • Is a "remember this" write tool wanted eventually? If yes, the confidence policy is the decision, not the tool — and it should be settled before the read tool trains anyone to expect a write one.
