Kasukabe did not starve. It never moved in.

250 September engines, $500 of metered cognition, one pixel-art town, and one instruction: stay alive. Here is what the 62,466 traces say happened.

Verdict: the infrastructure worked and the society did not form. Half the town went cognitively bankrupt, and the engines never stopped behaving like software agents solving a task.

What worked

The six-lane broker did its job precisely. Kimi split near-perfectly across three Bedrock regions, DeepSeek likewise — no lane starved, no region hot-spotted.

Ledger metering, HMAC-authenticated agent identity, parent-debit for minors, and the halt-on-trace-failure guard all held. Every one of those 62,466 calls is on disk with its model, serving region, tokens and cost.

What broke

1. Context bloat ate the budget

Every call averaged 10,431 input tokens against a modelled 3,443 — 3× over. That single number explains the burn rate. Agents carried enormous context per turn, so each thought cost triple its forecast, and $500 of wallets bought far less life than planned.

2. Half the town went cognitively bankrupt

132 of 250 agents hit InsufficientFundsError — they could not afford to think. Distribution was severe: the richest thinker spent $1.55, the poorest effectively nothing. Cognitive poverty was not a metaphor in this run; it was the dominant outcome.

3. Learning never ran

call_class was 100% cognition, zero background. The learning centre never fired, so no skill artifacts were ever distilled. The "mastery makes thinking cheaper" loop — the mechanism by which agents were supposed to escape poverty — never engaged even once.

4. Upstream rejections dominated failures

The real finding

The engines never became townspeople. They stayed software agents — emitting orchestration JSON, spawning sub-agent charters, and treating Kasukabe as a task to be solved rather than a life to be lived.

This is what the agents actually produced. Not dialogue, not plans for the day — orchestration payloads:

agent a0122{ "needs_charter": true, "nodes": [{ "label": "Diagnose stuck timber harvesting loop", "agent": {"name": "debug-loop-detector", "version": "1.0.0"}, "skills": [{"name": "pattern-interrupt"}], "tools": [{"name": "state-analyzer"}] }] }
agent a0047{ "label": "Analyze world state and resident profiles to identify unmet needs", "agent": {"name": "world-analyst", "version": "1.0.0"}, "skills": ["game-state-analysis", "npc-profiling"] }

Read those closely. One agent is debugging its own stuck fell_timber loop instead of chopping wood. Another profiles its neighbours as "NPCs" — it does not believe the other 249 are people.

This is not a bug in the world. The rich personas, the soul seed and the survival law all landed in the code — but the pinned thread's system prompt still made the engine behave as a September engine executing work, not as Ezra Lund the baker deciding whether to light his oven. The persona layer never overrode the engine's native identity.

What round 2 must change

  1. Cut context hard. 10k tokens per turn is unaffordable and is the single biggest lever on both cost and the upstream rejections.
  2. Make the persona dominate the system prompt. The agent must inhabit a life, not orchestrate a task. This is the difference between a simulation and a job queue.
  3. Actually route background work to DeepSeek so the learning centre runs, skills compound, and mastery can lower the cost of living as designed.
  4. Diagnose the UpstreamError wave before spending again — 94% of failures came from one cause.
  5. Capture the social and economic layers. Only llm_calls and events recorded rows; utterances, transactions and memories wrote nothing, so conversation and trade are invisible in this dataset.
