# Fifty residents on the team box

What to install, what to put in `.env`, how to survive the 4-hour cap, and the
three numbers that decide whether the run finishes. Read alongside
[`docs/TEAM_BOX_GUIDE.md`](../docs/TEAM_BOX_GUIDE.md), which owns access and
etiquette; this file owns the run.

---

## First, one correction worth money

**The box has no GPU, and this project does not want one.** Every token is
generated by a remote provider — Bedrock today, OpenAI for this run. The box
runs Python, a SQLite trace and some headless Chrome; none of that touches a
GPU. The guide's spec — **32 CPUs, 64 GB RAM, no GPU** — is exactly right, and
a GPU instance would cost several times more for no extra throughput.

What the box is short of is **wall-clock hours**, not compute.

---

## The three numbers

| | |
|---|--:|
| ticks needed to spend $60 at 50 residents on `gpt-6-luna` | **362** |
| measured pace at 20 residents | **0.68 min/tick** (median, 91 consecutive ticks) |
| so: run length | **4.1 h** at that pace · **5.7 h** if 40% slower · **8.2 h** if half speed |

Against the box's rules:

| rule | value | consequence |
|---|---|---|
| per start | **4 hours**, off even mid-job | the run **will** be cut at least once |
| team budget | **~10.5 h total, shared, for good** | a 4–8 h run leaves little for anyone else |
| idle | 15 minutes, no job and nobody connected | not a risk while a run is ticking |

**The run cannot finish in one sitting.** It must be resumed, which works:
`trial-day2-20` was cut and resumed four times and the budget carried across
every restart, because the burned balance lives in the checkpoint.

**Check the start page's remaining budget before you begin.** If it reads under
about 6 hours, lower the `$60` cap rather than hope for the fast case — the run
still reaches the day-2 election and the day-3 boundary on less.

## Access

Your key is already made and its public half is on your machine at
`~/.ssh/id_ed25519.pub`. Paste that one line into **Add your SSH key** on the
start page, wait a minute, then **Start the box** and use the `ssh team@ADDRESS`
command the page shows. The address changes every start, so copy it each time;
at a new address SSH asks whether to continue — type `yes`.

`Permission denied (publickey)` a moment after adding the key usually means it
has not propagated yet. Wait and retry before debugging anything.

## Setup, once per box lifetime

```bash
# 1. the code. NOT inside ~/work - that holds the team's research code
#    (spread_store.py) and is not ours to nest in.
cd ~ && git clone https://github.com/septemberai/kasukabe.git
cd ~/kasukabe/app

# 2. our own venv, deliberately NOT the shared /opt/venv. This project
#    needs engine dependencies (aiosqlite and friends) that nobody else on
#    the box asked for, and the guide says to announce anything added to the
#    shared environment. Keeping ours separate means we announce nothing.
uv venv .venv --python 3.12
uv pip install --python .venv/bin/python -e .

# 4. the six cameras need a browser and an encoder, and there is no sudo.
#    Both have user-local wheels, so neither needs root. Do this now: the
#    launcher refuses to start a video run that cannot record, and finding
#    that out after pressing Start wastes box budget.
uv pip install --python .venv/bin/python playwright imageio-ffmpeg
.venv/bin/python -m playwright install chromium

# 5. prove it, before the run rather than after
.venv/bin/python -c "
import sys; sys.path.insert(0, 'scripts')
from record_ui import find_chrome, find_ffmpeg
from pathlib import Path
c, f = find_chrome(), find_ffmpeg()
ok = Path(c).is_absolute() and Path(c).exists()
print('chrome :', c if ok else 'MISSING')
print('ffmpeg :', f or 'MISSING')
raise SystemExit(0 if (ok and f) else 'cannot record - see the refusal advice')"
```

`playwright install chromium` puts a Chromium under `~/.cache/ms-playwright`
and `imageio-ffmpeg` ships an ffmpeg binary in its wheel. `find_chrome()` and
`find_ffmpeg()` look in both places, so nothing needs a path set.

### `.env` — put this in `~/kasukabe/app/.env`, then `chmod 600 app/.env`

```bash
# --- the model for this run -------------------------------------------
OPENAI_API_KEY=sk-...                  # the key, pasted on the box only
ONLY_MODEL=gpt-6-luna                  # one model and no other, every call class
OPENAI_RPM=500                         # OpenAI's account limit, not Bedrock's 100

# --- Bedrock stays configured as the fallback -------------------------
AWS_ACCESS_KEY_ID=...
AWS_SECRET_ACCESS_KEY=...
AWS_REGION=ap-south-1
BEDROCK_INFERENCE_PROFILES=...         # copy from the laptop's .env

# --- the rest ----------------------------------------------------------
WORLD_BASE_URL=http://127.0.0.1:8100
```

**Do not put `SPEND_CAP_USD` or `TRACE_SQLITE_PATH` here.** The launcher sets
both in the environment when it starts the broker and the runner, computed from
the scenario — the cap as `budget_cap_usd + $5` for the end-of-run drain. A
value in `.env` is at best ignored and at worst a second, disagreeing answer to
"what may this run spend".

The budget lives in **one** place: `budget_cap_usd` in the scenario file.

`ONLY_MODEL` is the switch that matters, and it is a rule rather than a
preference: Kimi and deepseek leave the order entirely, for every call class,
so there is no overflow onto Bedrock at any load. `COGNITION_FIRST_MODEL` only
*prefers* a model and only for thinking calls — under it the background work
still went to Bedrock every time, $1.43 of trial-day2-20's $20.16.

A missing key is then a boot-time refusal, not a fallback.

## Check before spending anything

```bash
cd ~/kasukabe/app
# the broker suite is what gates this run - it is the lane, the pricing and
# the allowlist. ~2 seconds. The world suite takes 5.5 minutes of a shared
# 8.4-hour budget and gates nothing here, so it is not worth the box time.
.venv/bin/python -m pytest broker/tests -q                 # 504 expected

# is the box free enough to take us? 32 CPUs, and a load over 28 means full.
uptime

.venv/bin/python -c "
from broker.config import BrokerSettings
from broker.lanes import build_lane_pool, CallClass
s = BrokerSettings.from_env()
p = build_lane_pool(s, lambda m, r: None)
print('lanes :', {m: len(v) for m, v in p.lanes_by_model.items()})
print('order :', p.preference_for(CallClass.COGNITION))"
```

`order` must be exactly `('gpt-6-luna',)` — one model, nothing behind it.
Anything else in that tuple means `ONLY_MODEL` did not load and the run can
still overflow onto Bedrock. If the key is missing the check raises instead of
printing an order, because the broker refuses to build a pool that cannot
serve the only model it is allowed to use.

### Our share of the 32 CPUs

The guide budgets experiments at 4 threads each, about 8 at once. This run is
not one experiment: it is the world, the broker, the game loop and **six
headless Chromes at 1920×1080**, which together sit nearer 8–12 CPUs. That is
within one team member's fair share of a quiet box and too much for a busy one.
If `uptime` shows a load above about 16 before starting, cut the camera list in
the scenario to two views (`town-with-buildings`, `live-chats`) and tell whoever
else is on.

## Run it

```bash
tmux new -s fifty
cd ~/kasukabe/app
./run-scenario.sh world/scenarios/fifty_from_day_two.json fifty-day2-20260929 4
```

Detach with `Ctrl-b` then `d`. Reattach with `tmux attach -t fifty`.

The three arguments are the scenario, the run name and a **wall-clock ceiling in
hours**. The `$60` cap is not one of them — it comes from the scenario file, and
the broker's own ceiling is set to $65 automatically so the end-of-run learning
drain has room. `CAP=40 ./run-scenario.sh ...` overrides it for one run.

The `4` is a race the box will probably win: its cut counts from when you pressed
Start, and the run begins a few minutes later. A hard cut is recoverable — it was
survived four times in `trial-day2-20` — so this is a safety net, not the plan.

### When the 4-hour cap stops it

Press **Start the box** again, reconnect at the new address, and continue:

```bash
tmux new -s fifty
cd ~/kasukabe/app
RESUME=1 ./run-scenario.sh world/scenarios/fifty_from_day_two.json fifty-day2-20260929 4
```

The budget continues with it. `system:burned` is written into the checkpoint, so
a resumed run does not get a fresh $60 — which is the behaviour you want and the
reason the cap still means something across restarts.

Connected terminals get a warning **30 minutes before the team budget ends**. If
you see it, stop the run and copy the results off; a report from an incomplete
run is worth more than bytes on a box that will not start again.

If the resume is refused for a stale lock:

```bash
rmdir /tmp/kasukabe-runseries.lock
```

If preflight blocks on prompt size (a known `learning_centre` issue inside the
Law 1 freeze), start anyway and watch the budget:

```bash
RESUME=1 KASUKABE_SKIP_PREFLIGHT=1 ./run-scenario.sh world/scenarios/fifty_from_day_two.json fifty-day2-20260929 4
```

## Watching it

```bash
cd ~/kasukabe/app

# spend, from the trace - the number that matters
.venv/bin/python -c "
import sqlite3
d = sqlite3.connect('file:data/fifty-day2-20260929.db?mode=ro', uri=True)
print('\$%.2f' % ((d.execute('select sum(cost_nano_dollars) from llm_calls').fetchone()[0] or 0)/1e9))"

# which model is actually serving - run this in the first ten minutes
.venv/bin/python -c "
import sqlite3
d = sqlite3.connect('file:data/fifty-day2-20260929.db?mode=ro', uri=True)
for m, n, c in d.execute('select model, count(*), sum(cost_nano_dollars)/1e9 from llm_calls group by 1'):
    print(f'{m:24} {n:>6,} calls  \${c:.2f}')"
```

Under `ONLY_MODEL` that query should show one model and one only. Any second
row means Bedrock is being billed after all — stop and fix `.env`.

### The report, while the run is still going

`report.md` is rewritten every **120 seconds** for as long as the run is alive —
the same report the run ends with, as far as it has got:

```bash
less ~/kasukabe/docs/runs/series/fifty-day2-20260929/report.md
```

Safe because every connection the generator opens is `mode=ro`, and atomic
because each pass writes to `.report.next` and moves it into place. A failed
pass keeps the last good report. `REPORT_EVERY=60` changes the interval;
2.1s per pass on a 116 MB trace is under 2% of one core at the default.

On a machine that stops after four hours whether the run finished or not, this
is the difference between a readable run and an interrupted one.

## The six views, and proving they are really being filmed

The scenario asks for six cameras, each its own headless Chrome on its own
DevTools port, all filming the same live world:

| view | what it shows |
|---|---|
| `town-with-buildings` | the map, roofs on |
| `town-without-buildings` | the same map, roofs off — people visible indoors |
| `live-chats` | the group chats as they happen |
| `election` | candidacy, campaigning and the count |
| `money` | the ledger and price boards |
| `government` | the seats and what the ministry does |

A run has one truth and many faces, and afterwards nobody can ask the other
five — the world is gone. That is why they run at once rather than one being
chosen.

**The launcher now refuses to start a video run it cannot record.** Chrome's
stdout and stderr go to `/dev/null` — correct for a working camera, and it
means a *missing* Chrome is silent: six empty directories and a report nobody
can watch, discovered when the $60 is already spent. The check is asked once,
of `record_ui.py`'s own `find_chrome()`, before anything starts.

While it runs, confirm frames are really landing — a directory that exists is
not a directory being written to:

```bash
cd ~/kasukabe
watch -n 30 'ls docs/runs/series/fifty-day2-20260929/video/*/frames | wc -l; \
  du -sh docs/runs/series/fifty-day2-20260929/video/*'
```

Each view should be gaining a frame every 4 seconds. If one view is flat while
the others climb, read `docs/runs/series/fifty-day2-20260929/record-<view>.log`.

**Frame numbering continues across a restart.** `record_ui.py` counts the
frames already on disk and carries on from there, so the 4-hour cut does not
start the video over or overwrite what was filmed. The mp4 is encoded from the
whole sequence when the run ends.

To run without video at all — only if recording cannot be made to work, since
the report, trace and 50 session logs are the evidence and video is the
nice-to-have:

```bash
NO_VIDEO=1 ./run-scenario.sh world/scenarios/fifty_from_day_two.json fifty-day2-20260929 4
```

## Finishing, and this part is not optional

```bash
# 1. on the box, see what there is to take
ls ~/kasukabe/docs/runs/series/fifty-day2-20260929

# 2. on YOUR computer, using the address from the start page
scp -r team@ADDRESS:kasukabe/docs/runs/series/fifty-day2-20260929 ./fifty-day2-20260929

# 3. back on the box: close the session. An idle tmux session counts as
#    work, keeps the box on, and spends everyone's remaining hours.
tmux kill-session -t fifty && exit
```

**Copy the results off before the team budget runs out.** The box's disk
survives a stop — that is why `RESUME=1` can continue from `app/data/fifty-day2-20260929.db`
at all, and it is why the guide's advice to keep things in `~/results` is a
convention rather than a survival requirement here. But at **zero budget** the
box turns off for good and will not start again, and anything only on its disk
is gone then.

## Honest risks, in the order they are likely to bite

1. **The team budget is the binding constraint.** 4.1 h is the optimistic
   estimate and ~10.5 h is all that is left for everyone.
2. **50 residents has never been run on this seeded economy.** The largest so
   far is 30, and that run predates every fix since. Expect surprises in the
   first hour.
3. **`gpt-6-luna` has never served a turn here.** The lane is proven against
   recorded OpenAI response shapes, not the live API. The first real call is the
   first proof, which is why the model-mix query above runs early.
4. **Pace at 50 is extrapolated from 20.** A tick waits for its slowest
   resident, so more residents means more chances to be slow.
